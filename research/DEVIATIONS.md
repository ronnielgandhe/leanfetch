# deviations from PREREGISTRATION.md

logged as they happened. none of them were decided from quality numbers.

1. **T1 pilot cut to 2 documents (not 20).** the 2-document check cost 0.12 usd per document across the 10-model ladder (graphrag sends two long requests per document). 18 more pilot documents would have spent about 2.2 usd on plumbing only. the 2 documents confirmed that every model returns parseable graphrag records. pilot documents are not in the main sample.
2. **T1 main n = 150, not 200.** this is the preregistered budget rule: projected main cost at n = 200 was about 24.5 usd for T1 alone. at n = 150 the projected total for the whole study was about 21.7 usd, under the 25 usd cap, so no model was dropped at that point. the first 150 main documents are used.
3. **gemini calls use the v1beta endpoint.** the v1 endpoint rejects system instructions and json mode. same models, same prompts.
4. **analysis code was run on pilot data for T2 and T3 after the preregistration commit** to check that it works. pilot quality numbers were therefore visible before the main runs. the margin, metrics and decision rule were already committed and were not changed.
5. **entity-name normalizer bug fix (T1), before any T1 main call.** inspecting the 2 pilot documents showed Few-NERD's tokenized possessives ("Gould 's") and spaced punctuation ("St . Louis") never matching the model's "GOULD". the normalizer now drops a trailing possessive and spaces before `.`, `'` and `-`. same rule for gold and predictions, every model. scores are recomputed from saved raw text in `stage4_analyze.py`, so the fix applies everywhere.
6. **ledger race fix.** the first T3 and T2 main runs read `spend.json` while another thread was writing it, which raised `JSONDecodeError` before the request was sent on 20 T3 calls and a few dozen T2 calls (no tokens spent on those). writes are now atomic and reads are locked; the failed items were re-run with identical requests. totals are cross-checked by `stage7_spend.py`, which sums the cost of every cached response.
7. **T2 empty-statement replies scored the way haystack scores them.** my first scorer treated `{"statements": [], "statement_scores": []}` as a parse failure. haystack's `FaithfulnessEvaluator._postprocess_results` gives such a reply a score of 0 (unfaithful). the scorer now does the same. this affected 9 gpt-5.6-terra replies; all 9 were on right (faithful) answers, so they are wrong under both rules and no T2 number changed. found while checking parse-failure rates, after the T2 main results were visible; it is a faithfulness-to-the-repo fix, applied to every model.
8. **T1 normalizer brought in line with the preregistered rule, with the old one kept as a sensitivity check.** the preregistration says names are normalized by stripping punctuation except `&` and `.`. the code that ran through the pilot (v1) kept apostrophes and hyphens, which left Few-NERD tokenization artifacts unmatched ("University of Hawai ' i", "Brunch Squad & amp", "Frisian People 's Party"; 74 of the main-sample gold names have such spacing). v2 does what the preregistration says: drop possessive 's, turn `&amp;` into `&`, replace every other punctuation mark with a space. this was written after provisional T1 numbers for six models were visible, so `results/t1_main.json` reports the decision under both normalizers (`sensitivity_normalizer_v1`), and a T1 claim is only made in the paper if it holds under both.
9. **T1 main run restarted (twice).** it stalled for about 20 minutes during the gpt-5-nano block (no new responses, connections open). i killed it and started the same command again. every finished response was already cached, so the restart only re-sent the requests that were in flight; nothing about the data or the analysis changed.
   the cause turned out to be the laptop sleeping with the lid closed, which broke in-flight connections that then waited out long read timeouts. the second restart lowered the client timeouts (openai 180 -> 150 s, anthropic 300 -> 200 s; the slowest normal T1 call was 85 s). four gpt-5-nano T1 calls have recorded latencies around 2,150 s because they spanned a sleep; latency numbers for gpt-5-nano on T1 are therefore not meaningful, and latency was never part of any decision.
10. **T1 main stopped before gpt-5.6-terra and claude-sonnet-5-5 finished.** with the laptop lid closed the run only advanced during brief wake windows, and the last two models would have taken hours more. i stopped it with 47 of 150 documents done for gpt-5.6-terra and none for claude-sonnet-5-5 (beyond the 2 pilot documents). neither can change the T1 verdict: the rule only counts alternatives that cost at most half the default per call, and both cost more than gpt-4.1 per document (gpt-5.6-terra measured on its 47 finished documents: $37,782 per million, 1.57x; claude-sonnet-5-5 on the pilot: about $47,000 per million, about 2x). they are left out of the T1 tables rather than shown on partial data. running `stage3_run.py t1 main --limit 150` again resumes from the cache. this also left about 12 usd of the budget unspent.
